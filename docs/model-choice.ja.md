# モデルを選ぶ

**[English](model-choice.md)** · **[中文](model-choice.zh-CN.md)** · **日本語**

健康データをどこで処理できるかを選び、次に本機のハードウェアと画像理解のニーズを考えます。
Mirobody は全ローカル・クラウド・ハイブリッドの構成に対応しています。チャット・文書抽出・日記の記録は、それぞれ別のモデルを使えます。

## デプロイの選択肢

| 優先すること | 構成 | 必要なもの |
| --- | --- | --- |
| モデル処理をすべてローカルにとどめる | チャットに MiniCPM5-2B、文書に GLM-OCR-0.9B | メモリ 16 GB のコンピューター。GPU 不要 |
| ローカルにとどめつつ画像を直接理解する | チャットに Qwen3.8-27B、文書に GLM-OCR-0.9B | メモリ 32 GB の Mac、または VRAM 24 GB の NVIDIA GPU |
| ローカルの推論ハードウェアなしでクラウドモデルを使う | 設定済みのクラウドモデル | モデル API キー。提供元はタスクに必要なデータを受け取ります |
| 文書画像をローカルにとどめつつクラウドの回答を使う | ローカルの GLM-OCR とクラウドのチャットモデル | ローカルの OCR サーバーとモデル API キー |

セットアップページはローカルモデルとクラウドモデルの両方に対応しています。ハイブリッド構成には `.env` の設定が必要です。CPU のみでの回答は、ハードウェア・モデル・会話内容によっては数分かかることがあります。

## ローカルモデル

既定のローカル構成は、Q8_0 の重みを使う MiniCPM5-2B です。より大きな構成は、IQ3_S の重みとビジョンプロジェクターを使う Qwen3.8-27B です。どちらも文書認識には GLM-OCR-0.9B を使います。

推論は [llama.cpp](https://github.com/ggml-org/llama.cpp) の `llama-server` で動き、モデルは初回利用時に Hugging Face からダウンロードされます。プラットフォームごとの GPU・CPU 構成は[ローカルでの実行](local-models.ja.md)を参照してください。

<a id="the-document-reader-glm-ocr-09b"></a>

### 文書と写真

GLM-OCR が報告書から文字と表を抽出します。認識できた表のレイアウトはルールが読み取り、
残りの文章はモデルが処理します。軽量なチャットモデルは写真の OCR 文字を受け取るだけで、
見た目を推測することはできません。より大きなチャットモデルは画像を直接確認できますが、
食事の内容やカロリーの推定など、解釈が誤っていることもあります。

## クラウドモデルへ送るデータ

クラウドモデルを使うと、ローカルのハードウェア要件を減らせます。キーを設定したら、
モデル選択メニューから使える項目を選びます。

| データまたはタスク | 完全ローカル | クラウド構成 | ローカル OCR + クラウドチャット |
| --- | --- | --- | --- |
| 報告書の写真とスキャンページ | ローカルで処理 | 視覚モデルに送信 | ローカルで処理 |
| 文書の文字 | ローカルで処理 | ローカルの表抽出後に残った文字を送信。先頭 3,000 文字はタイトルと要約の生成にも使用 | 同じ範囲の文字を送信 |
| 質問とエージェントが取得した行 | ローカルにとどまる | チャットの提供元に送信 | チャットの提供元に送信 |
| チャットに添付した画像 | モデルに応じて OCR 文字またはローカルの視覚を使用 | チャットモデルが画像に対応していれば送信 | チャットモデルが画像に対応していれば同様に送信 |
| 用語と単位の標準化 | オフライン | オフライン | オフライン |

ローカル OCR は文書画像をローカルにとどめますが、文字はそれでも外部に送られることがあります。チャットの画像は、アップロードしたファイルとは別に、チャットモデルの設定に従います。

<a id="health-data-on-openrouter"></a>

### OpenRouter のホスト選択

OpenRouter は複数のホストにリクエストを振り分けることがあり、ホストごとにデータ保持条件と対応パラメータが異なります。セットアップページでのキー設定や `OPENROUTER_CHAT_MODEL`
の指定では、ホストは固定されません。アカウントのデータ設定とホストの規約の両方を確認してください。

記録されている評価ではゼロデータ保持を必須とし、モデルごとに1つのホストを固定してフォールバックなしで実施しました。これらの設定は `extra_body` 内の `provider.order` と `allow_fallbacks: false` で行います。[評価用の設定](../benchmarks/local_models/refs/)を参照してください。これらはルーティングと保持方法を制御するだけで、処理自体は外部で行われます。

## ハイブリッド構成

GLM-OCR を使えるローカルモデルサーバーを起動してから、次を設定します。

```bash
OPENROUTER_API_KEY=sk-or-...
LOCAL_OCR_BASE_URL=http://host.docker.internal:8080/v1
UTILS_VISION_MODEL=local-utils
```

`LOCAL_OCR_BASE_URL` を設定すると、クラウドのキーがあっても報告書の画像はローカルの OCR
に送られます。`UTILS_VISION_MODEL=local-utils` は、食事の写真など文字を抽出できないファイルもローカルにとどめます。その場合、説明はローカルで生成されるか、生成されません。

チャットの画像については、クラウドのチャット項目に `supports_image: false` を設定し、
OCR 文字を受け取るようにします。ハイブリッド構成は `.env` とモデル項目を直接編集して設定します。

## モデルの切り替えと確認

- **セットアップページ：** `./deploy.sh` が表示するリンクを開くか、**設定 → モデル**に進みます。キーとモデル名を入力するか、**100% このマシンで実行**とローカル構成を選びます。
  選択内容は検証・暗号化され、再起動なしで適用されます。
- **環境変数：** `LOCAL_MODEL` と `LOCAL_OCR_MODEL` はローカルモデルを選びます。
  `OPENROUTER_CHAT_MODEL` と `OPENROUTER_UTILS_MODEL` は OpenRouter のキーで使うモデルを選びます。`DEFAULT_MODEL`、`UTILS_TEXT_MODEL`、`UTILS_VISION_MODEL`、`UTILS_OCR_MODEL`
  は設定項目を選びます。`.env` を変更したら `docker compose up -d` を実行してください。
  再起動だけでは読み込み直されません。高度な設定は[設定](https://docs.mirobody.ai/ja/configuration)と [`config.llm.yaml`](../config.llm.yaml)
  を参照してください。

選択されている経路は次で確認します。

```bash
docker compose exec mirobody mirobody doctor --probe
```

このプローブは、ストリーミングチャットのツール呼び出しの往復に加え、文書抽出・視覚・OCR を確認し、チャットモデルが思考を表示したかどうかを報告します。必要なときだけ思考するモデルは、プローブの短い質問では思考しないことがあるため、思考がないことは注意として示すだけで、失敗にはしません。ローカルモデルの名称も検証します。プローブが成功しても、それが示すのはこれらの機能が動くことだけで、回答の質や応答速度は保証しません。

## 思考と最終回答

チャットは、対応しているインターフェースを通じて思考を要求します。`AGENT_THINKING` の既定値は `medium` で、モデル項目で有効化された `thinking_level` があればそちらが優先されます。ユーティリティタスクはそれぞれの設定のままです。「思考とツール」パネルには、返された思考とツールの活動が表示され、最終的な文章はそのモデルのステップが終わってから表示されます。一部のエンドポイントは推論内容を返さないことがあり、その場合はプローブがそれを報告します。
Mirobody が推論を作り出すことはありません。
